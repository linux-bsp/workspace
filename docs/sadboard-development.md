# SadBoard 调试功能开发与验收

在 `SadBoard` 分支维护实验层，复用 AM62x 已实机验证的 BSP、EDK、Linux 和
U-Boot 固定提交。固件版本保持 v0.0.1，以内容 SHA256 区分构建。案例始终需要
手动触发，不作为启动服务运行；随机组合在稳定单故障案例完成后再开发。

当前：阶段 1、2、3 已完成实机验收；下一阶段为隔离网络与内核 panic 现场。
统一入口、参数、记录格式与复位方法见 [场景生命周期](scenario-lifecycle.md)。
各案例须同步提供 [原理与定位手册](cases/README.md)，包括内核源码路径、工具参数、
取证过程、修复对照和练习；以实机结果校正教学内容。

## 阶段与验收门槛

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 1 调试基线与崩溃分析 | systemd、工具链、匹配符号、首个 GDB/core 案例 | OTA 成功、工具实际运行、在线堆栈/源码可读、core 可离线分析、参考修复通过 |
| 2 内存与性能 | cgroup OOM、CPU 热点、线程锁等待 | 有界复现、取得 OOM/perf/线程等待证据、修复对照、清理后恢复基线 |
| 3 场景入口与验收 | 统一列表、参数、现场目录、场景元数据和检查 | 指定案例可重复执行、失败明确、检查不因程序提前退出而误报成功 |
| 4 网络与内核现场 | 独立网络命名空间的延迟/丢包、手动 panic 与恢复取证 | 网络对照指标、日志保留和重启恢复；不更改承载 OTA/SOL 的 eth0 链路 |

每阶段均完成主机回归、镜像检查、OTA 实机验收，再提交/推送对应源码与 workspace
子模块指针。未通过则保留现场继续修复。正常确认完成前不触发实验故障，避免把主动
实验当成 OTA 试启动失败。根文件系统 A/B 布局和启动链沿用 BSP。

## 统一现场要求

- 记录案例、参数、固件完整 ID、内核版本、命令、退出码和证据路径。
- 应用、跟踪和采样结果写 `/data/sadboard/`，不把大文件放进 tmpfs。
- 故障版与参考修复版使用同一输入对照；性能案例要求业务结果一致。
- 每个案例文档包含现象、前提、触发、分级提示、根因、修复和复位步骤。
- 诊断内核与性能基线分开构建；KGDB、lockdep/kmemleak 选项保留为独立配置。
- 主机符号、sysroot 与设备镜像必须匹配，不能混用其他构建的 vmlinux 或程序。

阶段结果只记录到 [AM625 实机验证](am625-debug-validation.md)，不以构建成功替代上板结论。
