# EDK libbmc 与 SadBoard 专利候选分析

分析日期：2026-11-09。

当前最值得优先整理技术交底的是跨启动阶段的双缓冲日志归档，以及基于启动镜像内容身份的 rootfs 精确恢复。libbmc 的遥测质量与时效约束、EDK 的端点身份校验可以继续检索；SadBoard 的工作量等价验证和受控 panic 恢复验证适合作为储备方向。

以下优先级表示进一步检索和准备交底书的价值，不代表授权概率。判断以中国发明专利为主，依据当前源码、既有测试及实机记录，并结合初步公开文献检索。尚未完成逐项权利要求对比，也未确认既有专利申请、首次公开时间及申请权归属。既有验证记录不表示本次重新执行了测试或实机实验。

## 跨启动阶段的双缓冲日志归档

建议题目：**一种跨启动阶段的故障日志保留、归档确认及缓存回收方法**。

### 已实现机制

1. R5 SPL、A53 SPL、U-Boot 和 Kernel 使用一致的布局接力记录；DDR 就绪前使用 SRAM 暂存，随后迁入 DDR。
2. 两个 bank 按代次交替使用，分别保留最后一次失败启动与恢复启动的记录。缓存 bank 与固件 A/B 槽是不同概念。
3. 追加时保存上一份有效前缀的长度和 CRC，便于识别复位中断的追加并提取可校验前缀。
4. 当前系统通过健康检查后冻结快照，后台按偏移上传。服务端复核各阶段长度和 CRC，持久提交后确认归档。
5. 设备收到两个快照的归档确认后，向内核提交对应 capture ID；内核核对后先使两个头部失效，再清除缓存，拒绝不匹配的旧确认。
6. 管理端结合恢复启动上下文、相邻代次和不同 bank 关联异常与恢复归档，并保存独立事故附件。

依据：[双缓冲启动日志](../edk/docs/device-manager/startup-buffers.md)、[U-Boot 记录实现](../uboot/u-boot-2026.04/common/bsp_bootlog.c)、[内核冻结与确认实现](../linux/linux-7.0/drivers/firmware/bsp_bootlog.c)、[设备上传实现](../edk/user/apps/logctl/startup-forward.c)、[服务端事故关联](../edk/user/apps/device-manager/server/sol/sol-startup-evidence.c)。

### 候选贡献与现有技术

候选贡献在于启动日志采集、双 bank 代次、冻结、服务端持久确认与设备清除之间的约束关系。它针对恢复启动覆盖故障记录、上传未完成就清除、旧确认误清新缓存，以及追加或清除被复位打断后的状态识别问题。

单独的“重启后保留 RAM 日志”已有公开方案：[ramoops](https://kernel.org/doc/html/next/admin-guide/ramoops.html) 和 [US7506203B2](https://patents.google.com/patent/US7506203B2/en) 均应纳入对比。不能仅凭保留内存、CRC 或两个缓存判断具备创造性。

### 证据与边界

[AM625 验证档案](am625-debug-validation.md)保留了 panic、恢复启动、四阶段日志和归档确认的实机记录。交底时仍需整理以下对比数据：恢复启动后的故障日志保留情况、确认丢失后的重试结果、错误 capture ID 的拒绝结果，以及追加或清除中断后的可恢复状态。

该机制面向保留 DDR 的复位，不保证断电保留。连续失败超过两个 bank 的容量会覆盖更早记录；未接入的 ROM、TIFS、ATF 输出及采集初始化前故障不属于完整性保证范围。

## 基于启动镜像内容身份的 rootfs 恢复

建议题目：**一种基于启动镜像绑定内容身份的嵌入式根文件系统恢复方法**。

### 已实现机制

1. 从经过校验的 kernel FIT/DTB 取得对应 rootfs 的长度、完整哈希和 verity 参数，约束恢复目标。
2. 按准确内容身份请求、验证恢复包，避免仅按服务器最新发布选择 rootfs，造成 kernel/rootfs 错配。
3. 在 RAM 根文件系统中修复选定 rootfs 并读回校验；备用 rootfs 的维护推迟到正常系统健康确认后执行。
4. 备用修复检查 pending/writing 事务、实际物理槽、记录身份和分区占用；块设备写入与读回期间持有独占分区 claim。
5. 修复完成不代替正式系统的健康确认，也不自行改变部署选择。

依据：[恢复引擎](../edk/user/apps/fwctl/core/dm_fw_recovery.c)、[initramfs 与备用维护实现](../edk/user/apps/fwctl/recovery/fw-init.c)、[固件恢复接口和限制](../edk/docs/device-manager/fwctl.md)。

### 候选贡献与现有技术

候选技术效果是恢复出与本次启动内核匹配的 rootfs，同时避免写入运行分区或干扰升级事务。应围绕内容绑定、恢复时机与物理槽保护的协作关系检索。

A/B、哈希校验和可信启动已有大量公开技术；[Android Verified Boot](https://source.android.google.cn/docs/security/features/verifiedboot/verified-boot?hl=en) 是重要对照。哈希完整性不等于发布者认证，交底中的可信来源假设必须与实际签名配置一致。

建议准备同版本不同内容、恢复包身份错误、备用槽被挂载、升级事务占用和读回失败的对比记录。现有软件检查及正常重启证据不能替代真实掉电测试。

## libbmc 遥测质量与时效约束

建议题目：**一种异构管理协议遥测数据的质量与时效约束输出方法**。

### 已实现机制

1. 将多个协议来源映射到稳定逻辑测点，并设置明确的来源优先级。
2. 快照分别保存最近尝试和最近有效样本，保留失败尝试信息。
3. 遥测输出检查质量、单位、采集时间、数值范围及线格式约束，区分失败、过期和不可用状态。
4. 仅在显式允许且仍满足时效条件时复用历史数值；明确不存在的设备不能通过历史数值继续表现为有效。
5. 健康、存在性和事件位采用各自投影规则，不直接沿用数值缓存复用策略。

依据：[来源选择](../libbmc/src/bmc/bmc_routing.c)、[快照模型](../libbmc/src/model/bmc_snapshot.c)、[遥测投影](../libbmc/src/epdu/bmc_epdu_snapshot.c)、[遥测契约](../libbmc/docs/telemetry.md)。

### 候选贡献与现有技术

具体问题是采集失败后，历史值被当作当前有效值输出，或单位、存在性和事件语义在协议切换中被混淆。候选贡献应落在来源选择、最近尝试、最近有效值、时效和输出状态之间的约束。

[US20260067358A1](https://patents.google.com/patent/US20260067358A1/en) 于 2026-03-05 公开，涉及 IPMI/Redfish 协议选择、传感器采集与统一格式。它说明“多协议统一采集”的宽泛方向已有较近文献；是否影响本候选的具体特征组合，仍需逐项比较。这一文献对照不构成侵权判断。

厂商字段适配应区分手册规则与新增机制。例如依照 iBMA 状态解释 CPU/内存字段，不能仅因实现了手册要求就主张为主要发明点。

建议整理协议来源切换、采集失败、设备缺席、缺失或未来时间戳、单位冲突和缓存过期时的输出对照。当前版本的完整真机测点覆盖、长期采集、OS Agent 状态变化和物理 UART 接收仍以 [libbmc 验证状态](../libbmc/docs/validation-report.md)为准。

## EDK 外设端点身份一致性

建议题目：**一种异构外设逻辑发现与访问端点身份一致性校验方法**。

### 已实现机制

PDI 按逻辑名称查询设备后，打开返回的节点，从实际文件描述符取得端点身份，再查询管理记录，核对查询前后与实际端点的 endpoint ID、设备类型和节点路径。身份不一致时关闭文件描述符，并在有限次数内重试。

依据：[PDI 查询与校验](../edk/user/lib/pdi/src/core/pdi_manager.c)、[PDM 端点身份与生命周期](../edk/kernel/pdm/core/pdm_cdev.c)。

该机制针对查询与打开之间设备解绑、节点重新使用导致的访问对象变化。可结合注册和端点生命周期提炼完整方案，但身份令牌、代次校验和竞态处理本身也较常见，需要证明超出常规运用的技术贡献。

### 现有注册管理草稿需要修正

[EDK 外设注册管理草稿](../edk/docs/patent_peripheral_registration_management.md)将“探测失败自动释放编号”列为机制和技术效果，当前实现与之不符：

- [总线 probe](../edk/kernel/pdm/core/pdm_bus.c)先调用 `pdm_device_bind()` 分配编号，再调用逻辑驱动的 probe。
- probe 失败后保留身份和编号，用于管理端诊断以及重试时复用。
- [解绑逻辑](../edk/kernel/pdm/core/pdm_device.c)负责相应身份与编号资源的撤销。

不能继续将“所有 probe 失败都会释放编号”写入当前实施例。也不能未经核对就声称所有硬件后端匹配完成后才分配编号。

注册表、设备树匹配、初始化逆序回滚和 SDK 封装可以组成方案，但不宜单独作为创造性结论。[Linux devres](https://cdn.kernel.org/doc/html/latest/driver-api/driver-model/devres.html)已提供资源管理和失败回滚机制。建议补充节点复用、绑定失败重试、身份冲突和解绑后访问的对比证据。

## SadBoard 工作量等价与证据完整性验证

建议题目：**一种基于工作负载等价约束和运行证据校验的嵌入式故障修复验证方法**。

### 已实现机制

1. CPU 案例固定输入规模、查询量和种子，独立计算期望 checksum，检查故障版与参考修复版的实际工作。
2. 锁案例检查完成数量和等待时间约束，识别跳过工作或等待造成的虚假加速。
3. core、pcap、OOM 等证据检查内容或结构，而非仅检查文件是否存在。
4. 实验记录绑定启动模式、固件或构建身份、boot ID、参数、独立结果目录及退出状态。
5. 使用受限服务、资源预算和独立网络命名空间控制实验影响范围，并保留取消、复位与不完整结果状态。

依据：[证据检查器](../sadboard-external/package/sadboard-labs/src/check-result.c)、[实验生命周期](../sadboard-external/package/sadboard-labs/sadboard)、[实机证据与负例检查](am625-debug-validation.md)。

### 候选贡献与当前边界

具体问题是修复版少处理数据、跳过等待或生成不完整证据，也可能被误判为修复成功。可以围绕工作量等价、独立结果计算与系统侧证据的联合验证继续检索，但要证明它超出常规回归测试断言的组合。

当前检查针对已知案例与参考实现，不是任意学习者修复方案的通用自动评分。性能输出仍包含人工判断，单次时间比值不能推定普遍性能提升。证据检查也不构成抵御恶意操作者伪造全部证据的认证机制。

网络启动模式中的 `SBNET1` 是构建参考身份，不证明可写 NFS 树始终未变；不能把它解释为运行内容的持续完整性证明。

随机故障编排、多故障组合、通用自动评分和确定性重放尚未实现，不应计入现有技术成果。后续若形成新的具体技术方案，应另行说明处理步骤和效果。

## SadBoard 受控 panic 与跨启动恢复验证

建议题目：**一种基于启动状态约束的嵌入式故障注入与跨启动恢复验证方法**。

### 已实现机制

1. 本地 A/B 模式要求固件先前已确认，且当前启动仍处于日志未封存窗口；网络调试模式要求同一构建已有健康启动记录。
2. 暂停健康确认进程，避免停止服务触发 OnFailure 并引入额外故障，随后记录实验意图并注入 panic。
3. 恢复后检查 boot ID 已变化、前一次记录的 Linux boot 与实验匹配，并检查 panic 观察结果和本次健康确认。
4. 本地 A/B 模式核对实际启动部署及完整固件内容 ID；网络模式核对 `SBNET1` 构建参考 ID，两者的证明范围不同。
5. 保存恢复结果和日志包，结合独立的失败与恢复启动归档分析现场。

依据：[panic 注入](../sadboard-external/package/sadboard-labs/run-panic)、[恢复检查](../sadboard-external/package/sadboard-labs/check-panic)、[启动证据语义](../edk/docs/device-manager/boot-evidence.md)。

### 候选贡献与现有技术

[LKDTM](https://kernel.org/doc/html/next/fault-injection/provoke-crashes.html)已提供故障构造和崩溃采集测试能力；[US20190205233A1](https://patents.google.com/patent/US20190205233A1/en)涉及故障注入、检测和恢复判定。因此，候选贡献应聚焦启动状态约束、避免监督策略引入额外故障，以及跨启动身份和证据关联。

软件重启意图、panic 观察和下一次 U-Boot 的复位标签具有不同语义，不能互相替代或直接等同于硬件根因。该方向与双缓冲启动日志存在技术重叠，应统一规划保护边界，避免重复包装相同贡献。

## 公开时间与申请权

### 公开时间需要先核实

2026-11-09 查询时，GitHub 显示 workspace 和 sadboard-external 为公开仓库，libbmc 为私有仓库；EDK 的可见性未能通过本次连接核实。当前私有不证明过去从未公开，Git 提交时间也不等于首次公开时间。

按[专利法第二十二条及第二十四条](https://ipc.court.gov.cn/zh-cn/news/view-6241.html)，申请前已为公众所知的技术可能影响新颖性；自行公开源码不自动适用六个月不丧失新颖性的例外。应按具体方案核实：

- 是否已有在先申请及其申请日或优先权日；
- 仓库首次公开或由私有转为公开的时间，以及当时公开的具体实现；
- 文章、公开演示、发行包和交付是否使相关技术内容可被公众获得。

本分析包含候选技术机制，进入公开仓库后也属于对外可获取的材料；首次公开范围应同时考虑源码、文档和发布附件。

### 新增贡献与申请权需要分开确认

Git 作者、仓库所有者和发明人不是自动等同的身份。需区分上游实现、厂商协议、合作方代码和对实质性技术特点作出的新增贡献。

按[专利法第六条](https://ipc.court.gov.cn/zh-cn/news/view-6241.html)，执行单位任务或主要利用单位物质技术条件完成的发明可能属于职务发明，申请权需要结合实际任务和合同确认。

授权还要求新颖性、创造性和实用性。国家知识产权局[第 84 号令对审查指南的修改](https://www.cnipa.gov.cn/art/2025/11/13/art_74_202560.html)强调针对权利要求限定的整体技术方案评价创造性；应将对解决技术问题作出贡献的特征写入权利要求，不能仅堆叠常见组件。

## 技术交底准备顺序

第一轮先为双缓冲启动日志和 rootfs 精确恢复各准备一份技术交底，并完成最接近公开方案的特征对比，再决定是否正式立项。每份交底至少包含：

1. 具体故障场景、约束条件与最接近的公开方案。
2. 区别特征、处理步骤、状态转换及异常清理路径。
3. 数据结构或布局图、正常时序图和异常时序图。
4. 与区别特征直接对应的对比实验，注明源码、镜像、硬件和原始证据。
5. 首次公开时间、贡献人员和申请权依据。

第二轮评估 libbmc 的质量与时效约束，以及 EDK 的端点一致性方案。SadBoard 先围绕已实现的工作量校验和跨启动恢复验证积累材料；课程形式、提示规则和尚未实现的随机编排不作为现有发明点。
