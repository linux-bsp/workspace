# AM625 可靠性与验证边界

## 产品范围

实际链路为卫星平台 ↔ AM625 ↔ 载荷服务器及其独立 BMC，各设备以网口接入交换机。
AM625 是数据与遥控遥测桥接设备，不能假定载荷 BMC 能控制它的供电、复位或物理串口。
本文保留工程约束，具体业务通信协议和硬件故障处置不作为已完成能力声明。

## 本地启动与恢复

- 已有有效部署时，启动、健康确认和回退不以管理服务器或校时成功为前提。
- 更新经非活动槽、冗余 metadata、内容校验和读回验证后进入试启动；重启通过
  本地健康确认且服务器收到结果才记作 OTA success。
- 恢复按 HWID、版本、完整内容 ID 和必要的 payload SHA256 精确匹配，不盲取最新包。
- ROM 固定从 tiboot3 A 进入；普通 kernel/rootfs OTA 不代表引导程序更新或恢复已经验收。
- JSON 打包配置与启动侧物理布局独立维护，由一致性检查把关；不在线迁移已部署分区。

操作与状态解释见 [升级指南](firmware-upgrade-guide.md)、
[BSP 恢复说明](../../bsp-base-external/board/ti/am625/verified-boot.md)。

## 日志、重启原因与时间

早期启动日志通过有限 RAM 缓冲接力；Linux 将可读取的证据归档并在联网后补传。
RAM 双缓冲和 ramoops 的保留依赖复位类型，不能当作物理掉电后仍保存的 ROM。
服务端归档确认与本地清理要区分，容量上限和截断状态必须可见。

硬件复位源、软件重启意图和崩溃痕迹是不同证据；缺少可靠关联时保持未知，不能
把恢复后的日志当作失败启动，也不能将零值复位寄存器直接认定为上电。
时间未同步时不把设备时间视为可信事件顺序；界面同时保留服务器接收时间和启动身份。
时间服务独立运行，显示 UTC+8。详见 EDK 的
[启动证据](../../edk/docs/device-manager/boot-evidence.md) 与
[时间管理](../../edk/docs/device-manager/time-sync.md)。

## 验证范围

当前发布记录以 AM625 SD 为主。构建通过、模拟存储测试、正常 OTA success 和
真实故障注入是不同层次。eMMC/NOR 实物、突然断电、更多复位来源、持续浸泡与
硬件 watchdog 期限只能由各自证据证明。

CRC/内容哈希检测损坏，不等于身份认证、生产签名或硬件防回滚已经部署。
当前管理网页保留显式开启的免凭据调试方式，SOL 是只读日志通道。
原生单元测试不证明端到端平台/载荷业务链路已验收。

现有结果与证据位置见 [AM625 索引](README.md#验证与溯源)。
