## 现象与原理

**生产现场与异常现象。** 跨平台协议原型正常，接入另一款处理器后报文长度变成巨大值并触发分配失败。

**原理与容易误判的地方。** 线上的字节序、整数宽度、结构体填充与对齐必须由协议定义。直接把字节缓冲强制转换成宿主结构可能把端序、padding 和未对齐访问问题叠加。

## 练习任务

设备端：运行“长度字段端序错误放大内存请求”故障现场，记录输出中的实际结果目录与异常证据。

```sh
sadboard run net-endian
```

设备端：执行“长度字段端序错误放大内存请求”的参考修复验收，核对终端结论及保存的结果契约。

```sh
sadboard verify net-endian
```

设备端：把路径占位符替换为本次实际现场目录，复核该次运行的证据完整性与验收约束。

```sh
sadboard check /srv/sadboard/实际目录
```

本例固定小负载，无额外参数；全部源文件安装在 `/usr/src/sadboard/src/`。实现入口为 [suite-network.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite-network.c)，公共调度器为 [suite.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite.c)。真实传输网络序长度 1024；本 ARM64 小端平台直接解释得到 262144，触发长度上限拒绝；参考 ntohl 后得到 1024，仍保留 4096 上限检查。

现场内 `net-endian-{bug,fixed}.out` 保存结构化度量，`.trace` 保存实际事件/资源计数，stderr/core/Valgrind 文件按案例保留。check 同时核对 trace 与摘要以及本例信号/业务契约，不会仅检查一个 passed 字符串。故障被限制在子进程或私有 namespace；run 返回的是取证控制器退出状态，真实异常信号要查看 observed/auxiliary 和 stderr，不能只看最外层 shell 的 `$?`。

**复现条件与故障注入。** 固定发送网络字节序长度 128，故障读者按宿主顺序解释；在受控进程内设置地址空间上限，禁止按错误长度分配整机级内存。参考版先 ntohl 再校验最大长度。 操作前记录版本/构建 ID、boot ID、输入、资源上限和超时。取证对象必须是自己的实验进程，设计卡中的 PID 均指该子进程。

**面试/评审追问。** packed 能否解决端序？为什么未对齐访问有时不崩溃但仍不能依赖？ 请提交：候选假设、可证伪实验、原始数据、关键源码分支、修复前后对照和未覆盖边界。只给一个参数调整或一个“修好了”的截图不算完成。

## 定位方法

**定位分析流程。** 以十六进制保存原始头，分别手工解码和 GDB x/b、p/x 检查；用 strace 查看错误尺寸的分配，而不是先给网络调大缓冲。 对照上方工具手册逐项说明命令回答了什么问题；信号/退出码、资源计数、业务完成数和时间轴必须能互相验证。优化前后采用同输入，至少保留一次负例，排除“异常只是没有触发”。

## 内核流程与汇编

**内核阅读入口。** [socket.c](https://github.com/linux-bsp/linux-7.0/blob/master/net/socket.c)：用户缓冲送入协议栈的边界；[fault.c](https://github.com/linux-bsp/linux-7.0/blob/master/arch/arm64/mm/fault.c)：未对齐/访问异常的架构背景。先确认用户态接口或信号，再向对应内核分支追踪；这些是本仓库 Linux 7.0 的源码入口，不是已经采集到的动态调用栈。

## 修复与验收

**修复方案与代价。** 使用固定宽度字段与 memcpy/明确序列化，所有长度在乘法和加法前先进行上限及溢出检查。

**量化验收与现场恢复。** 同一线格式在不同端序模型下得到相同业务长度，非法长度在分配前拒绝，正常帧内容不变。 最后停止实验进程，释放私有文件、描述符或 namespace；保存证据再清理，不删除系统日志，不影响管理网络。
