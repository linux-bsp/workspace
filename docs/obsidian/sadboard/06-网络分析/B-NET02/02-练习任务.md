# 练习任务

[[首页]] · [[06-网络分析/00-章节导航|章节导航]] · [[06-网络分析/B-NET02/00-案例导航|本例导航]] · [[案例索引]] · [[工具索引]]

```sh
sadboard run net-framing
sadboard verify net-framing
# 使用上一步打印的实际目录：sadboard check /srv/sadboard/实际目录
```

本例固定小负载，无额外参数；全部源文件安装在 `/usr/src/sadboard/src/`。实现入口为 [suite-network.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite-network.c)，公共调度器为 [suite.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite.c)。真实 TCP 流先发 3 B，接收者读到前缀后握手允许发送后续 9 B，不依赖随机时序。故障单次 recv 把短读误判为完整消息失败；参考重组 12 B 并校验 8 B 载荷。

现场内 `net-framing-{bug,fixed}.out` 保存结构化度量，`.trace` 保存实际事件/资源计数，stderr/core/Valgrind 文件按案例保留。check 同时核对 trace 与摘要以及本例信号/业务契约，不会仅检查一个 passed 字符串。故障被限制在子进程或私有 namespace；run 返回的是取证控制器退出状态，真实异常信号要查看 observed/auxiliary 和 stderr，不能只看最外层 shell 的 `$?`。

**复现条件与故障注入。** 独立 netns 中发送带长度的两条消息，故意把头和体分多次发送；故障读者假设一次 recv 一条消息，参考版维护累积缓冲和解析状态。 操作前记录版本/构建 ID、boot ID、输入、资源上限和超时。取证对象必须是自己的实验进程，设计卡中的 PID 均指该子进程。

**面试/评审追问。** send 返回全部长度是否表示对端业务已处理？TCP 可靠传输为什么仍需要应用层协议？ 请提交：候选假设、可证伪实验、原始数据、关键源码分支、修复前后对照和未覆盖边界。只给一个参数调整或一个“修好了”的截图不算完成。
