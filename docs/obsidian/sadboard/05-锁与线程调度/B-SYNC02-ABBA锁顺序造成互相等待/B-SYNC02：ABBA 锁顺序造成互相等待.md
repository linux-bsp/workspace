## 现象与原理

**生产现场与异常现象。** 设备重连与配置更新同时发生，两个线程都活着但业务停止。

**原理与容易误判的地方。** 形成环形等待才是死锁的核心证据。看到 futex 等待并不够，还要找到每个锁的拥有者和等待边；把锁全部换成递归锁并不能消除线程间的环。

## 练习任务

设备端：运行“ABBA锁顺序造成互相等待”故障现场，记录输出中的实际结果目录与异常证据。

```sh
sadboard run sync-abba
```

设备端：执行“ABBA锁顺序造成互相等待”的参考修复验收，核对终端结论及保存的结果契约。

```sh
sadboard verify sync-abba
```

设备端：把路径占位符替换为本次实际现场目录，复核该次运行的证据完整性与验收约束。

```sh
sadboard check /srv/sadboard/实际目录
```

本例固定小负载，无额外参数；全部源文件安装在 `/usr/src/sadboard/src/`。实现入口为 [suite-sync.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite-sync.c)，公共调度器为 [suite.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite.c)。故障两个线程在各自持有第一把锁后用 barrier 同步，确定性形成 ABBA。父进程超时后只杀掉本实验子进程；参考版统一锁顺序完成两个结果 42。

现场内 `sync-abba-{bug,fixed}.out` 保存结构化度量，`.trace` 保存实际事件/资源计数，stderr/core/Valgrind 文件按案例保留。check 同时核对 trace 与摘要以及本例信号/业务契约，不会仅检查一个 passed 字符串。故障被限制在子进程或私有 namespace；run 返回的是取证控制器退出状态，真实异常信号要查看 observed/auxiliary 和 stderr，不能只看最外层 shell 的 `$?`。

**复现条件与故障注入。** 两个私有线程经 barrier 同步，分别先持有 A/B 再尝试 B/A；第二次获取使用有限 timedlock，确保实验会退出。参考版统一顺序或一次性协议获取。 操作前记录版本/构建 ID、boot ID、输入、资源上限和超时。取证对象必须是自己的实验进程，设计卡中的 PID 均指该子进程。

**面试/评审追问。** 死锁、活锁、饥饿和锁竞争分别如何举证？ 请提交：候选假设、可证伪实验、原始数据、关键源码分支、修复前后对照和未覆盖边界。只给一个参数调整或一个“修好了”的截图不算完成。

## 定位方法

**定位分析流程。** GDB thread apply all bt，标记两个 mutex 地址和拥有者，strace -f -T -e futex 对齐超时；画等待图。 对照上方工具手册逐项说明命令回答了什么问题；信号/退出码、资源计数、业务完成数和时间轴必须能互相验证。优化前后采用同输入，至少保留一次负例，排除“异常只是没有触发”。

参数查阅：[[工具手册/trace-cmd|本方向基础工具参数与边界]]。

## 内核流程与汇编

**内核阅读入口。** [waitwake.c](https://github.com/linux-bsp/linux-7.0/blob/master/kernel/futex/waitwake.c)：futex_wait、futex_wake；[rtmutex.c](https://github.com/linux-bsp/linux-7.0/blob/master/kernel/locking/rtmutex.c)：PI 锁路径，与普通锁区别。先确认用户态接口或信号，再向对应内核分支追踪；这些是本仓库 Linux 7.0 的源码入口，不是已经采集到的动态调用栈。

## 修复与验收

**修复方案与代价。** 定义全局锁层级，缩短持锁范围并避免持锁回调；超时返回不应让半完成事务继续污染对象。

**量化验收与现场恢复。** 竞争场景完整完成且锁最终释放；超时、取消、错误路径也遵守相同锁顺序。 最后停止实验进程，释放私有文件、描述符或 namespace；保存证据再清理，不删除系统日志，不影响管理网络。
