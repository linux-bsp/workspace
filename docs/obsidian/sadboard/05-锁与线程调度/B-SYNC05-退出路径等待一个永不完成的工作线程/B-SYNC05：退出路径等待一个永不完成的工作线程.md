## 现象与原理

**生产现场与异常现象。** 服务停止超时，被 systemd 强杀；主线程栈停在 pthread_join，真正阻塞点在另一个线程。

**原理与容易误判的地方。** 内存中的退出标志不会自动唤醒阻塞系统调用。join 所等待的是目标线程结束，不是它内部的一把业务锁；必须跨线程追踪到实际 I/O 或条件等待。

## 练习任务

设备端：运行“退出路径等待一个永不完成的工作线程”故障现场，记录输出中的实际结果目录与异常证据。

```sh
sadboard run sync-shutdown
```

```sh
sadboard verify sync-shutdown
```

设备端：把路径占位符替换为本次实际现场目录，复核该次运行的证据完整性与验收约束。

```sh
sadboard check /srv/sadboard/实际目录
```

本例固定小负载，无额外参数；全部源文件安装在 `/usr/src/sadboard/src/`。实现入口为 [suite-sync.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite-sync.c)，公共调度器为 [suite.c](https://github.com/linux-bsp/sadboard-external/blob/93c81e82acfdf5d54155d1b9bb750e78645d384f/package/sadboard-labs/src/suite.c)。接收线程阻塞 read；故障版先 join 返回 ETIMEDOUT，参考版先 shutdown 唤醒再 join。超时后故障版也会唤醒并 join，FD 最终回基线。

现场内 `sync-shutdown-{bug,fixed}.out` 保存结构化度量，`.trace` 保存实际事件/资源计数，stderr/core/Valgrind 文件按案例保留。check 同时核对 trace 与摘要以及本例信号/业务契约，不会仅检查一个 passed 字符串。故障被限制在子进程或私有 namespace；run 返回的是取证控制器退出状态，真实异常信号要查看 observed/auxiliary 和 stderr，不能只看最外层 shell 的 `$?`。

**复现条件与故障注入。** 私有 worker 阻塞读取管道，故障主线程仅设置退出标志便 join；用外部三秒 timeout 保底。参考版通过关闭相应端点或事件通知解除等待，再 join。 操作前记录版本/构建 ID、boot ID、输入、资源上限和超时。取证对象必须是自己的实验进程，设计卡中的 PID 均指该子进程。

**面试/评审追问。** 为什么设置 atomic<bool> stop 仍可能无法停止线程？关闭 fd 与并发读取有哪些竞态？ 请提交：候选假设、可证伪实验、原始数据、关键源码分支、修复前后对照和未覆盖边界。只给一个参数调整或一个“修好了”的截图不算完成。

## 定位方法

**定位分析流程。** 同时采集全部线程栈与 strace -ff；检查 stop 时哪些 fd 被关闭、退出标志何时可见以及是否发出唤醒通知。 对照上方工具手册逐项说明命令回答了什么问题；信号/退出码、资源计数、业务完成数和时间轴必须能互相验证。优化前后采用同输入，至少保留一次负例，排除“异常只是没有触发”。

## 内核流程与汇编

**内核阅读入口。** [pipe.c](https://github.com/linux-bsp/linux-7.0/blob/master/fs/pipe.c)：pipe_read；[waitwake.c](https://github.com/linux-bsp/linux-7.0/blob/master/kernel/futex/waitwake.c)：线程退出与等待相关 futex 路径。先确认用户态接口或信号，再向对应内核分支追踪；这些是本仓库 Linux 7.0 的源码入口，不是已经采集到的动态调用栈。

## 修复与验收

**修复方案与代价。** 设计可取消的等待协议，区分正常 EOF 与停止事件；清理顺序须避免工作线程继续使用已销毁的对象。

**量化验收与现场恢复。** 服务在预算内退出、子线程和 fd 全部回收，下一次启动仍正常；不能以固定 SIGKILL 作为正常停止方案。 最后停止实验进程，释放私有文件、描述符或 namespace；保存证据再清理，不删除系统日志，不影响管理网络。
