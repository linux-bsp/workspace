# trace-cmd

[[首页]] · [[工具索引]] · [[案例索引]]

## 解决的问题

保存和解码内核事件，分析线程切换、唤醒与调度延迟。

## 工作原理与准备

基于内核跟踪机制录制事件。sched_wakeup 表示线程变为可运行，sched_switch 表示实际运行切换；二者之间的间隔需要结合 TID 与 CPU 时间线分析。

## 录制与分析

ftrace 是内核跟踪框架，tracefs 暴露控制与缓冲区。trace-cmd 负责配置、录制和解码，
不是另一个内核跟踪实现。SadBoard 的准备服务挂载 debugfs/tracefs，不自动开全量跟踪。

设备端：将本次 NFS/SD 模式的实际结果根目录保存为当前终端变量，供后续命令复用。

```sh
SADBOARD_RESULTS=$(sadboard results)
```

设备端：查看可用 tracer，核对当前内核是否提供所需跟踪器。

```sh
cat /sys/kernel/tracing/available_tracers
```

设备端：查看事件列表的开头；具体 sched 事件是否存在还需按后文名称确认。

```sh
cat /sys/kernel/tracing/available_events | head -20
```

设备端：采集一秒 sched_switch 事件，确认 trace-cmd 能生成有效数据文件。

```sh
trace-cmd record -o ${SADBOARD_RESULTS}/sched.dat -e sched:sched_switch -- sleep 1
```

设备端：解码刚才的 sched.dat，确认其中实际存在调度事件。

```sh
trace-cmd report -i ${SADBOARD_RESULTS}/sched.dat
```

`record` 录制，`-e SUBSYSTEM:EVENT` 选择事件，`-o` 保存二进制，`report -i` 解码。
`sched_switch` 说明谁让出/获得 CPU，`sched_wakeup` 说明何时变成可运行；把两者和 TID
联系起来才能区分睡眠与唤醒后的调度延迟。

## 判断边界

先确认事件存在与采集范围，使用自己的输出路径，检查丢失事件。wakeup 不代表立即获得 CPU，不能把全部墙钟延迟归为锁持有时间。底层接口见 [[工具手册/ftrace]]。
